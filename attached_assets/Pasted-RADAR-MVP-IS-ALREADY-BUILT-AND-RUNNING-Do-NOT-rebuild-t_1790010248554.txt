==================================================
GOAL
====

Build RADAR's first real lead-discovery pipeline.

The first milestone is:

A user can create a Radar such as:

“Find Indian consumer brands that could benefit from UGC.”

RADAR should search real publicly available web information, identify real companies, research them, qualify them against the Radar criteria, collect supporting evidence, and return real lead records.

The system must NEVER fabricate companies, people, emails, URLs, social accounts, events, or evidence.

==================================================

Keep all existing functionality:

Add:

DEMO MODE | LIVE MODE

Live Mode should use real providers.

If providers are unavailable or API keys are missing, show a clear error/state instead of silently falling back to fictional data.

==================================================
ARCHITECTURE
============

Use the existing provider abstraction.

Do NOT hardcode one provider throughout the application.

Create/complete provider interfaces similar to:

SearchProvider
ResearchProvider
EnrichmentProvider
VerificationProvider

The application should depend on these interfaces rather than directly depending on a specific vendor.

This will allow providers to be replaced later.

==================================================

1. RADAR QUERY INTERPRETATION
   ==================================================

When the user creates a Radar, convert the natural-language request into structured criteria.

Example:

User:

“Find Indian brands that could benefit from UGC.”

Structured representation:

Target:
Consumer brands

Location:
India

Potential offer:
UGC

Signals:

* active online presence
* product suitable for visual demonstration
* active social presence
* recent product/activity signals
* limited creator-style content

Keep the original natural-language query as well.

The user should be able to see/edit the interpreted criteria before running the Radar.

==================================================
2. SEARCH PROVIDER
==================

Connect a real web/search provider.

Use environment variables for credentials.

Do NOT expose API keys to the frontend.

Create a provider adapter.

Conceptually:

searchCandidates(criteria)

returns normalized candidate records:

* name
* url
* snippet
* source
* discoveredAt

Do not assume search results are companies.

The next stage must verify/research candidates.

If a provider cannot be configured yet, keep the provider interface and provide a clear configuration error.

Do NOT generate fake search results.

==================================================
3. CANDIDATE NORMALIZATION
==========================

Normalize search results.

Deduplicate candidates using:

* canonical URL
* domain
* normalized company name

Do not create multiple leads for the same company simply because it appeared in several search results.

==================================================
4. WEB RESEARCH
===============

For each candidate, research publicly available web information.

Create a ResearchProvider.

The research layer should attempt to determine:

* company name
* official website
* description
* industry
* location
* products/services
* publicly visible social profiles
* recent publicly observable activity
* relevant business signals

Use a web-crawling/research provider where appropriate.

Do not crawl private or authenticated areas.

Respect provider/platform terms and applicable laws.

==================================================
5. SIGNAL EXTRACTION
====================

Extract observable signals.

Examples:

Website exists
Active social presence
Recent product launch
Recently updated website
Hiring
New location
New service
Press/news mention
Strong product visual potential
Limited creator-style content

Each signal must have:

* statement
* source URL
* source name
* observed date/time where available
* confidence/status

Never turn an inference into a fact.

For example:

FACT:
“Company published a new product page.”

INFERENCE:
“This may create an opportunity for product-focused UGC.”

The UI should distinguish these.

==================================================
6. QUALIFICATION
================

RADAR should determine whether a candidate actually matches the user's Radar.

Do NOT use an arbitrary black-box score alone.

Instead produce:

MATCH

GOOD FIT
POSSIBLE FIT
NOT A FIT

And explain why.

Example:

GOOD FIT

Why:

* Indian consumer brand
* Active online presence
* Recent product activity
* Product is suitable for visual demonstration
* Limited creator-style content detected

The qualification decision must be based on collected evidence.

==================================================
7. EVIDENCE
===========

Every important lead claim should have evidence.

Store:

Evidence:

* leadId
* type
* statement
* sourceUrl
* sourceName
* observedAt
* confidence

Examples:

“Company launched Product X.”

Source:
official company website

or:

“Company posted about Product X.”

Source:
public company page

Do not cite search results as if they were the original source when the original source is available.

==================================================
8. REAL LEAD RECORD
===================

Once a candidate passes qualification, create a real Lead record using the existing database model.

Populate:

* companyName
* website
* description
* industry
* location
* socialProfiles
* signals
* evidence
* relevanceReason
* opportunity
* source
* discoveredAt
* radarId
* status

Do not invent missing information.

Unknown values should remain null/empty and display:

“Not found”

or

“Not verified”

==================================================
9. CONTACTS
===========

DO NOT build aggressive contact scraping yet.

For Phase 2, only store contact information if it is obtained from an approved/connected provider or is clearly publicly available through permitted sources.

Do not guess email addresses.

Do not construct emails such as:

[firstname@company.com](mailto:firstname@company.com)

unless an actual source verifies them.

If no contact is found:

CONTACT NOT FOUND

This is acceptable.

We will build a dedicated contact-enrichment phase later.
